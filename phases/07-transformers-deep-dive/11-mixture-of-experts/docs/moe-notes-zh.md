# MoE（混合专家模型）核心问答笔记

> 本文是关于 Mixture of Experts（MoE）的中文补充笔记，围绕几个最容易产生误解的问题展开：
> 路由到底怎么选专家？稀疏性到底省在哪里？容量（capacity）究竟解决什么问题？
> 正课请见 [en.md](./en.md)。

## 1. 基本设定

- 一个 MoE 层包含 **E 个专家**（expert），每个专家是一个独立的 FFN（通常比稠密模型的 FFN 更小）。
- 一个**路由器**（router / gating network）为每个 token 输出 E 维 logits。
- 每个 token 根据 logits 选择 **top-k 个专家**（k ≪ E，常见 k=1 或 k=2）来处理它。

## 2. 选专家时有没有"温度"？会不会随机采样？

**推理时：没有。** 标准做法就是对路由器 logits 做确定性的 top-k 选择——排序、取前 k 个，没有温度参数，也没有随机采样。原因：

1. **确定性**——同样的输入得到同样的路由结果，可复现；
2. **效率**——top-k 是一次简单的排序/argmax，采样反而增加开销；
3. **一致性**——模型在训练中收敛到的路由分布，推理时应该原样使用。

**训练时：可以有随机性。** 一些实现会在训练阶段引入随机成分来改善探索和负载均衡，例如：

- **Noisy Top-K**（Shazeer et al., 2017）：在 logits 上加可学习的噪声再取 top-k；
- **Gumbel-Softmax + 温度**：让离散选择可微，温度控制随机程度。

但这些都是**训练期的正则化手段**，推理时全部去掉，回到确定性 top-k。

## 3. 稀疏性到底省在哪里？——"每个专家都小"还不够

一个常见误解：既然每个专家的 FFN 更小，那让每个专家处理**全部** n 个 token 也没关系吧？

**不行——那样 MoE 的计算优势就完全消失了。** 设输入 X 形状为 (n, d)：

| 方案 | 计算量（相对单个专家 FFN） |
|------|--------------------------|
| 稠密大 FFN，处理 n 个 token | ≈ n × （大 FFN 成本） |
| MoE 稀疏路由：每个 token 只进 k 个专家 | ≈ k·n × （小 FFN 成本），与 E 无关 |
| "MoE 但每个专家吃全部 n 个 token" | ≈ E·n × （小 FFN 成本）——白白多算 E/k 倍 |

MoE 的收益来自两件事的**组合**：

1. **专家更小**——省的是参数带来的单次计算成本；
2. **稀疏路由**——每个专家平均只处理约 k·n/E 个 token，省的是总计算量（FLOPs）。

只有第 1 条、没有第 2 条，等于把一个 FFN 切成 E 份然后每份都跑一遍全部 token——毫无意义。**稀疏性的本质是"每个 token 不经过所有专家"**，这才是 "Sparse MoE" 中 "sparse" 的含义。

## 4. 路由是按 token 进行的——不连续、可重叠

两个常见误解，答案都是否定的：

- **专家必须处理连续的一段 token 吗？不必。** 每个 token 独立地由路由器决定去向，同一个专家收到的 token 在序列中通常是散落的，不是连续区间。
- **一个 token 只能被一个专家处理吗？不是（k>1 时）。** top-k 路由下，一个 token 会被 k 个专家分别处理，产生 k 份输出，再按路由权重加权求和。

以 k=2 为例：

```text
token 0: router → [0.80, 0.10, 0.05, 0.05] → top-2 = 专家 {0, 1}
         输出 = w0·FFN0(x0) + w1·FFN1(x0)

token 1: router → [0.30, 0.05, 0.60, 0.05] → top-2 = 专家 {2, 0}
         输出 = w2·FFN2(x1) + w0·FFN0(x1)
```

此时专家 0 处理了 token {0, 1}，专家 1 处理了 {0}，专家 2 处理了 {1}——分配既不连续也不互斥。权重 w 通常取路由器对被选中专家的 softmax 概率（在 top-k 内重新归一化）。

一句话总结：**路由是 per-token 的；每个 token 可以被多个专家处理，最终输出是这些专家输出的加权和。**

## 5. 容量（Expert Capacity）解决的不是"总内存"

每个专家常设一个**容量上限**：最多处理 C 个 token。一个自然的疑问：

> 假设 E=2、k=1、输入 1000 个 token。全部路由给专家 1 用 1000 份内存；均分给两个专家是 500+500，**总内存一样**——容量根本没省内存啊？

这个观察是对的：**总内存确实一样**。容量真正解决的是**倾斜（skew）**问题，来源于工程现实：

### 5.1 专家并行（Expert Parallelism）：专家分布在不同设备上

实际部署中，专家 1 在 GPU 1 上、专家 2 在 GPU 2 上。如果 1000 个 token 全部涌向专家 1：

- GPU 1 干 1000 个 token 的活，GPU 2 完全闲置——**墙钟时间由最忙的专家决定**，你付出了稠密计算的延迟，却没得到任何稀疏的好处；
- 总内存虽然不变，但**单设备内存**不同：GPU 1 要装下全部 1000 个 token 的激活，而 GPU 2 的内存闲着。OOM 看的是单卡，不是总量。

### 5.2 静态缓冲区形状（Static Shapes）

token 在设备之间通过 **all-to-all 通信**交换，这要求预先分配固定大小的缓冲区：每个专家一个形状为 `(C, d)` 的张量。编译期无法预知路由器会怎么分配 token，所以只能固定缓冲区大小并强制执行。这一设计源自 TPU/XLA 时代（Switch Transformer 就诞生于此），那里动态形状基本不可行。

### 5.3 防止路由塌缩（Routing Collapse）

没有任何约束时，路由器可能学会把所有 token 都发给同一个专家——稀疏性名存实亡。容量上限配合**负载均衡辅助损失**（load-balancing auxiliary loss）迫使路由分散。常用 **capacity factor** 给出松弛量，例如：

```text
C = capacity_factor × (k × n / E)      # capacity_factor 常取 1.0 ~ 1.25
```

即在"完美均衡负载"的基础上放宽 25% 左右。

## 6. 容量满了之后，溢出的 token 去哪？

继续上面的例子：容量设为 750，专家 1 已收满 750 个 token，剩下 250 个怎么办？

**经典 Switch Transformer 的答案：直接丢弃（drop），不会转发给专家 2。** "丢弃"的含义是这些 token **跳过本层 FFN**，仅靠残差连接原样传给下一层：

```text
x_out = x_in + FFN_expert(x_in)   # 正常 token
x_out = x_in                       # 被丢弃的 token —— 原样直通
```

残差流让这件事是可以承受的：token 的表示继续向前传播，只是错过了这一层的 FFN 更新。训练中负载均衡损失会把丢弃率压到很低（通常百分之几）。

其他变体的处理方式：

- **top-2 回退**：首选专家满了，token 落到它的次选专家上；
- **Expert Choice 路由**（反转视角）：不是 token 选专家，而是**每个专家挑选自己得分最高的 C 个 token**——构造上不可能溢出（但可能有 token 没被任何专家选中，本质上还是另一种形式的丢弃）；
- **推理时小 batch**：很多实现干脆关闭容量限制，按路由结果如实处理——丢弃机制主要是训练期和大批量服务期的关注点。

## 7. 想打平稠密模型的能力，每个专家要多大？

一个自然的问题：稠密 FFN 大小为 N，拆成 E 个专家后，每个专家要多大才能达到**同等的推理能力**？

答案不是 N/E——因为 **MoE 的参数"含金量"低于稠密参数**。一个总参数 `P_total`、每 token 只激活 `P_active` 的稀疏模型，表现并不等于稠密的 `P_total` 模型，而是介于两者之间。一个常用的经验法则是取**几何平均**作为"等效规模"：

```text
P_effective ≈ √(P_active × P_total)
```

### 7.1 用这条法则推算专家尺寸

设每个专家大小为 s、共 E 个专家、top-k 路由：

- `P_total = E·s`，`P_active = k·s`
- 要打平大小为 N 的稠密 FFN：`√(k·s × E·s) = N`，解得 **`s = N / √(kE)`**
- 对应总参数 **`E·s = N·√(E/k)`**——永远大于 N

以 E=8、k=2 为例：

| 量 | 大小 | 与稠密 N 相比 |
|----|------|--------------|
| 每个专家 s | N/4 | — |
| 总参数 E·s | 2N | 2 倍内存 |
| 每 token 激活 k·s | N/2 | 一半计算量 |

这就是 MoE 交易的本质：**用约 2 倍的内存，换取同等质量下约一半的推理计算量。** 反过来，如果每个专家只有 N/E（总参数恰好为 N、激活 kN/E），能力会明显低于稠密 N 模型——这也是为什么现实中的 MoE 模型总参数总是远大于其"稠密等效"规模（Mixtral 8×7B：总参数 47B、激活约 13B，能力大致对标稠密 34B~70B，正好落在激活量与总量之间，与法则的预测一致）。

### 7.2 两条重要限定

1. **这是经验法则，不是定律。** 真实的换算关系取决于训练数据量、专家粒度（DeepSeek 式细粒度专家会改变曲线）、负载均衡质量等，估算精度大约 ±30%，只能用于规划。
2. **"推理能力"恰恰是对 MoE 最不利的场景。** 一致的经验证据表明：稀疏扩容对**知识型**任务（事实召回、记忆——随总参数扩展）帮助更大，对**推理型**任务（更贴近每 token 实际执行的计算量，即激活参数）帮助较小。直觉是：推理由每个 token 真正执行的计算完成，而 MoE 恰恰在这上面做了节省。所以如果目标是推理能力对齐而非困惑度对齐，应该往悲观方向取值——更大的专家或更高的 k。这也解释了为什么一些新模型在重视推理时会保持较高的 k、加一个始终激活的**共享专家**（shared expert），或者转而扩展深度/注意力而不是继续加大稀疏度。

## 8. MoE 到底怎么省计算——逐项算一遍 FLOPs

先固定符号，避免歧义（尤其注意：**H 是宽度，第 7 节的 N 是参数规模**，两者不是一回事）：

| 符号 | 含义 |
|------|------|
| d | token 向量维度（模型宽度） |
| H | 稠密 FFN 的隐藏宽度（hidden features 个数） |
| h | 每个专家的隐藏宽度 |
| E / k | 专家总数 / 每 token 激活的专家数 |
| n | 一批输入的 token 数（第 3、5 节用到） |

参数量正比于 d×宽度，所以第 7 节按参数规模推出的换算 `s = N/√(kE)` 对宽度同样成立：`h = H/√(kE)`。

### 8.1 稠密 FFN：每个 token 的计算量

标准 FFN 把维度为 d 的 token 向量升维到隐藏宽度 H，过激活函数，再降回 d：

```text
z = act(x · W1)      W1 为 d×H   →  ≈ 2·d·H FLOPs
y = z · W2           W2 为 H×d   →  ≈ 2·d·H FLOPs
──────────────────────────────────────────────────
每 token 合计                      ≈ 4·d·H FLOPs
```

（系数 2 来自每次乘加算一次乘法加一次加法；关键是一切都**正比于 d·H**。）

代入具体数字：d=1024、H=4096 → 每 token 约 **1680 万 FLOPs**。

### 8.2 MoE 版本：每个 token 的计算量

换成 E 个专家、每个专家隐藏宽度为 h、top-k 路由：

```text
路由器:  x · W_r     W_r 为 d×E  →  2·d·E FLOPs（可忽略）
k 个专家，每个:                    ≈ 4·d·h FLOPs
──────────────────────────────────────────────────
每 token 合计                      ≈ k·4·d·h + 2·d·E
```

**每个 token 只为它实际经过的 k 个专家付计算费。** 其余 E−k 个专家对这个 token 贡献 0 FLOPs——它们的权重只是躺在显存里。所以每 token 计算量正比于 k·h，**E 完全不出现在计算成本里**（除了可忽略的路由项）。

同样的数字：E=8、h=1024、k=2：

- 专家计算：2 × 4 × 1024 × 1024 ≈ **840 万 FLOPs**——稠密的一半
- 路由器：2 × 1024 × 8 ≈ 1.6 万 FLOPs——占 0.1%，噪声级

即 **1680 万 → 840 万 FLOPs，计算量减半**；代价是总参数从稠密的 2·d·H ≈ 840 万个权重变为 8 × 2·d·h ≈ 1680 万个——**内存翻倍**。

### 8.3 一行总结与"解耦"

计算量减少的条件就是 `k·h < H`：

```text
稠密计算量  ∝ d·H
MoE 计算量  ∝ d·k·h        缩减倍数 = H / (k·h)
```

MoE 把稠密模型里焊死在一起的两样东西**解耦**了：

- **每 token 计算量**随**激活宽度**扩展：∝ k·h
- **模型容量**（知识、参数量）随**总宽度**扩展：∝ E·h

稠密模型里两者都是同一个 H——想加容量必须加计算。MoE 里可以把 E 加大来堆容量，而 k·h（也就是 FLOPs、也就是延迟）保持不变。

注意与第 7 节的公平比较：上面这组数字（激活宽度 H/2、总宽度 2H）按几何平均法则等效规模恰为 √(H/2 · 2H) = H，正好打平稠密模型。所以这笔交易的精确表述是：**同等质量下，每 token FLOPs 减半，代价是权重内存翻倍。** MoE 不是凭空省计算，而是拿内存换计算——所以它赢在内存充裕、FLOPs/延迟是瓶颈的场景（大规模服务），而在内存紧张的场景（单张消费级显卡）并不划算。

### 8.4 "隐藏层变小了"只说对了一半——总宽、单 token 窄

一个容易走偏的总结："MoE 的意义就是隐藏层可以比稠密的小很多"。这只对了一半，两半都很关键：

- **每个 token 实际经过的**隐藏宽度（k·h）比 H 小——计算节省来自这里；
- **实际存在的总**隐藏宽度（E·h）比 H 大得多——质量来自这里。

沿用上面的例子：稠密 H=4096；MoE 有 8×1024=**8192 个隐藏单元**（总宽是稠密的 2 倍），但每个 token 只经过 2×1024=**2048 个**（单 token 宽度是稠密的一半）。

如果只是把稠密模型的隐藏层从 4096 砍到 2048，计算量同样减半——但质量会下降，因为所有 token 被迫共用同一小组特征。MoE 真正做的是：

> **把隐藏层建得比稠密的更宽，但让每个 token 只使用其中为它单独挑选的一小片。**

让"切片"生效的是路由器。背后的赌注是：一个 token 并不需要全部 8192 个隐藏特征——代码 token 需要某一批，法语 token 需要另一批，算术 token 又是一批。如果路由器学会把每个 token 送到持有*它所需*特征的专家那里，那 token 经过的这 2048 个单元就能大致顶替稠密模型里 4096 个通用单元的作用，因为它们是为这个 token 选出的*正确*的 2048 个。这就是专家特化（specialization）的故事——也解释了为什么路由塌缩是致命的失败模式：所有 token 都挤向同几个专家时，你手里就真的只剩一个小稠密模型了。

一句话：**MoE 的隐藏层总量宽、单 token 窄，由学出来的路由器决定每个 token 走哪一窄片。计算量跟着窄片走，容量跟着总量走。**

## 9. 要点速查

| 问题 | 答案 |
|------|------|
| 推理时选专家有温度/随机性吗？ | 没有，确定性 top-k；随机性（Noisy Top-K、Gumbel）只出现在训练期 |
| 每个专家处理全部 n 个 token 行不行？ | 不行，那会把计算量放大 E/k 倍，稀疏性荡然无存 |
| 专家处理的 token 必须连续吗？ | 不必，per-token 路由，分配是散落的 |
| 一个 token 只能进一个专家吗？ | k>1 时进 k 个专家，输出加权求和 |
| 容量省的是总内存吗？ | 不是。它解决的是设备间负载倾斜、单卡内存峰值和静态通信缓冲区问题 |
| 容量满了溢出 token 去哪？ | Switch：跳过 FFN 走残差直通；top-2 可回退次选专家；Expert Choice 构造上无溢出 |
| 拆成 E 个专家，每个多大能打平稠密 N？ | 经验值 ≈ N/√(kE)，总参数 N·√(E/k)（大于 N）；推理型任务还要再加码 |
| MoE 省计算的本质？ | 计算量 ∝ 激活宽度 k·h、容量 ∝ 总宽度 E·h；隐藏层总量更宽、每 token 走的更窄，用内存换 FLOPs |
