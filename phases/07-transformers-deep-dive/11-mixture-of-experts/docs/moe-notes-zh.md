# MoE（混合专家模型）核心问答笔记

> 本文是关于 Mixture of Experts（MoE）的中文补充笔记，围绕几个最容易产生误解的问题展开：
> 路由到底怎么选专家？稀疏性到底省在哪里？容量（capacity）究竟解决什么问题？
> 正课请见 [en.md](./en.md)。

## 1. 基本设定

- 一个 MoE 层包含 **E 个专家**（expert），每个专家是一个独立的 FFN（通常比稠密模型的 FFN 更小）。
- 一个**路由器**（router / gating network）为每个 token 输出 E 维 logits。
- 每个 token 根据 logits 选择 **top-k 个专家**（k ≪ E，常见 k=1 或 k=2）来处理它。

## 2. 选专家时有没有"温度"？会不会随机采样？

**推理时：没有。** 标准做法就是对路由器 logits 做确定性的 top-k 选择——排序、取前 k 个，没有温度参数，也没有随机采样。原因：

1. **确定性**——同样的输入得到同样的路由结果，可复现；
2. **效率**——top-k 是一次简单的排序/argmax，采样反而增加开销；
3. **一致性**——模型在训练中收敛到的路由分布，推理时应该原样使用。

**训练时：可以有随机性。** 一些实现会在训练阶段引入随机成分来改善探索和负载均衡，例如：

- **Noisy Top-K**（Shazeer et al., 2017）：在 logits 上加可学习的噪声再取 top-k；
- **Gumbel-Softmax + 温度**：让离散选择可微，温度控制随机程度。

但这些都是**训练期的正则化手段**，推理时全部去掉，回到确定性 top-k。

## 3. 稀疏性到底省在哪里？——"每个专家都小"还不够

一个常见误解：既然每个专家的 FFN 更小，那让每个专家处理**全部** n 个 token 也没关系吧？

**不行——那样 MoE 的计算优势就完全消失了。** 设输入 X 形状为 (n, d)：

| 方案 | 计算量（相对单个专家 FFN） |
|------|--------------------------|
| 稠密大 FFN，处理 n 个 token | ≈ n × （大 FFN 成本） |
| MoE 稀疏路由：每个 token 只进 k 个专家 | ≈ k·n × （小 FFN 成本），与 E 无关 |
| "MoE 但每个专家吃全部 n 个 token" | ≈ E·n × （小 FFN 成本）——白白多算 E/k 倍 |

MoE 的收益来自两件事的**组合**：

1. **专家更小**——省的是参数带来的单次计算成本；
2. **稀疏路由**——每个专家平均只处理约 k·n/E 个 token，省的是总计算量（FLOPs）。

只有第 1 条、没有第 2 条，等于把一个 FFN 切成 E 份然后每份都跑一遍全部 token——毫无意义。**稀疏性的本质是"每个 token 不经过所有专家"**，这才是 "Sparse MoE" 中 "sparse" 的含义。

## 4. 路由是按 token 进行的——不连续、可重叠

两个常见误解，答案都是否定的：

- **专家必须处理连续的一段 token 吗？不必。** 每个 token 独立地由路由器决定去向，同一个专家收到的 token 在序列中通常是散落的，不是连续区间。
- **一个 token 只能被一个专家处理吗？不是（k>1 时）。** top-k 路由下，一个 token 会被 k 个专家分别处理，产生 k 份输出，再按路由权重加权求和。

以 k=2 为例：

```text
token 0: router → [0.80, 0.10, 0.05, 0.05] → top-2 = 专家 {0, 1}
         输出 = w0·FFN0(x0) + w1·FFN1(x0)

token 1: router → [0.30, 0.05, 0.60, 0.05] → top-2 = 专家 {2, 0}
         输出 = w2·FFN2(x1) + w0·FFN0(x1)
```

此时专家 0 处理了 token {0, 1}，专家 1 处理了 {0}，专家 2 处理了 {1}——分配既不连续也不互斥。权重 w 通常取路由器对被选中专家的 softmax 概率（在 top-k 内重新归一化）。

一句话总结：**路由是 per-token 的；每个 token 可以被多个专家处理，最终输出是这些专家输出的加权和。**

## 5. 容量（Expert Capacity）解决的不是"总内存"

每个专家常设一个**容量上限**：最多处理 C 个 token。一个自然的疑问：

> 假设 E=2、k=1、输入 1000 个 token。全部路由给专家 1 用 1000 份内存；均分给两个专家是 500+500，**总内存一样**——容量根本没省内存啊？

这个观察是对的：**总内存确实一样**。容量真正解决的是**倾斜（skew）**问题，来源于工程现实：

### 5.1 专家并行（Expert Parallelism）：专家分布在不同设备上

实际部署中，专家 1 在 GPU 1 上、专家 2 在 GPU 2 上。如果 1000 个 token 全部涌向专家 1：

- GPU 1 干 1000 个 token 的活，GPU 2 完全闲置——**墙钟时间由最忙的专家决定**，你付出了稠密计算的延迟，却没得到任何稀疏的好处；
- 总内存虽然不变，但**单设备内存**不同：GPU 1 要装下全部 1000 个 token 的激活，而 GPU 2 的内存闲着。OOM 看的是单卡，不是总量。

### 5.2 静态缓冲区形状（Static Shapes）

token 在设备之间通过 **all-to-all 通信**交换，这要求预先分配固定大小的缓冲区：每个专家一个形状为 `(C, d)` 的张量。编译期无法预知路由器会怎么分配 token，所以只能固定缓冲区大小并强制执行。这一设计源自 TPU/XLA 时代（Switch Transformer 就诞生于此），那里动态形状基本不可行。

### 5.3 防止路由塌缩（Routing Collapse）

没有任何约束时，路由器可能学会把所有 token 都发给同一个专家——稀疏性名存实亡。容量上限配合**负载均衡辅助损失**（load-balancing auxiliary loss）迫使路由分散。常用 **capacity factor** 给出松弛量，例如：

```text
C = capacity_factor × (k × n / E)      # capacity_factor 常取 1.0 ~ 1.25
```

即在"完美均衡负载"的基础上放宽 25% 左右。

## 6. 容量满了之后，溢出的 token 去哪？

继续上面的例子：容量设为 750，专家 1 已收满 750 个 token，剩下 250 个怎么办？

**经典 Switch Transformer 的答案：直接丢弃（drop），不会转发给专家 2。** "丢弃"的含义是这些 token **跳过本层 FFN**，仅靠残差连接原样传给下一层：

```text
x_out = x_in + FFN_expert(x_in)   # 正常 token
x_out = x_in                       # 被丢弃的 token —— 原样直通
```

残差流让这件事是可以承受的：token 的表示继续向前传播，只是错过了这一层的 FFN 更新。训练中负载均衡损失会把丢弃率压到很低（通常百分之几）。

其他变体的处理方式：

- **top-2 回退**：首选专家满了，token 落到它的次选专家上；
- **Expert Choice 路由**（反转视角）：不是 token 选专家，而是**每个专家挑选自己得分最高的 C 个 token**——构造上不可能溢出（但可能有 token 没被任何专家选中，本质上还是另一种形式的丢弃）；
- **推理时小 batch**：很多实现干脆关闭容量限制，按路由结果如实处理——丢弃机制主要是训练期和大批量服务期的关注点。

## 7. 要点速查

| 问题 | 答案 |
|------|------|
| 推理时选专家有温度/随机性吗？ | 没有，确定性 top-k；随机性（Noisy Top-K、Gumbel）只出现在训练期 |
| 每个专家处理全部 n 个 token 行不行？ | 不行，那会把计算量放大 E/k 倍，稀疏性荡然无存 |
| 专家处理的 token 必须连续吗？ | 不必，per-token 路由，分配是散落的 |
| 一个 token 只能进一个专家吗？ | k>1 时进 k 个专家，输出加权求和 |
| 容量省的是总内存吗？ | 不是。它解决的是设备间负载倾斜、单卡内存峰值和静态通信缓冲区问题 |
| 容量满了溢出 token 去哪？ | Switch：跳过 FFN 走残差直通；top-2 可回退次选专家；Expert Choice 构造上无溢出 |
