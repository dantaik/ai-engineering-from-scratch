# 预训练数据管线：模型是一面镜子

> 一句话总结：GPT-3、Llama 3、DeepSeek 的架构大同小异，效果天差地别，差距压倒性地来自数据。这一课回答三个问题：数据从哪来、怎么洗（重头是 MinHash 去重）、以及最根本的一个——给定算力预算，参数和数据到底该怎么分（Chinchilla 缩放律，本文把论文里的公式链条完整推一遍）。

这份笔记不是 `03-data-pipelines/docs/en.md` 的翻译。原文对 Chinchilla 只给了结论（`N_opt ~ C^0.5`），这里把它背后的三个公式和拟合常数完整展开；MinHash 部分补上原文没点透的那条数学性质（为什么最小哈希恰好能估计相似度）；清洗、打包等工程部分做了压缩，代码实现见原文 Build It。

---

## 1. 为什么说架构不是主角

三组数字放在一起看：GPT-3 用了 3000 亿 token，DeepSeek-V2 用了 8.1 万亿，Llama 3 用了 15.6 万亿。这三个模型的架构却大同小异——都是堆叠的 transformer 块。**输出质量的差距，压倒性地来自数据。**

模型是一面镜子：喂它什么，它就以完美的流利度反射什么。喂垃圾，它会把垃圾说得头头是道。

数据不仅要多，配比同样致命。Llama 3 公开了它的配方：约 50% 网页、25% 代码、13% 书籍和论文、8% 数学、4% 多语言网页。网页太多，模型变成 Reddit 复读机；代码太少，不会编程；数学太少，推理拉胯。**配比没有公式可循**——这是训练 LLM 最难的环节之一，只能靠实验和评测迭代。

## 2. 清洗流水线：六道工序

原始的 Common Crawl（约 250 TB）不是数据集，是垃圾场：HTML 标签、导航栏、Cookie 声明、SEO 垃圾、机器生成的注水文、个人隐私信息、编码错误的乱码。清洗不是可选项，它是"模型输出连贯段落"和"模型输出混着商品列表的 HTML 标签"之间的分界线。

```mermaid
graph LR
    A["原始文本"] --> B["剥 HTML"]
    B --> C["语言检测"]
    C --> D["质量过滤"]
    D --> E["去重"]
    E --> F["PII 清除"]
    F --> G["干净文本"]
```

每道工序各杀一类噪声，两道值得多说一句：

- **质量过滤的聪明做法是困惑度过滤**（RefinedWeb/Falcon 的路子）：用维基百科这类干净文本训一个小语言模型，拿它给每篇文档打分。困惑度高 = 这篇文档"不像人话"——大概率是垃圾词堆砌或机器生成。阈值以上直接扔。土办法也有效：太短的、全大写占比过高的（SEO 喊麦）、特殊字符占比过高的（乱码），三条规则就能筛掉惊人数量的垃圾。
- **去重是单项影响最大的一步。**Llama 团队报告去重删掉了约 **38%** 的网页数据——超过三分之一的 Common Crawl 是重复内容。重复数据不只浪费算力，还会让模型把特定段落背下来逐字复述（memorization），这既是质量问题也是隐私问题。

## 3. MinHash 去重：不比较每一对，也能找出近似重复

精确去重很简单——每篇文档算个哈希，相同就删。难的是**近似重复**：同一篇新闻被两个网站转载，正文 95% 相同，只是周围的广告不一样，字节级哈希完全不同。

衡量"近似重复"的标准尺子是 **Jaccard 相似度**：把两篇文档各变成一个集合，交集大小除以并集大小。但逐对计算是 O(n²)——十亿篇文档就是 5×10¹⁷ 对，死路。MinHash + LSH 用四步把它降到近线性：

**第一步，Shingling：文档 → 集合。**把文档切成所有连续 n 元组（比如 5 个词一组的滑窗）。这样"文档相似"就变成了"集合重叠"，Jaccard 有了用武之地。

**第二步，MinHash：大集合 → 定长签名。**取 k 个不同的哈希函数（比如 128 个），每个函数对集合里所有 shingle 求哈希、只记**最小值**。得到一个 128 维签名。这里藏着整个算法的数学灵魂，原文没有点透：

> **对一个随机哈希函数，两篇文档的最小哈希值相等的概率，恰好等于它们的 Jaccard 相似度。**
>
> 为什么：把两个集合的并集拿来看，哈希值最小的那个元素落在并集里的位置是均匀随机的。两边的最小值相等，当且仅当这个"全场最小"恰好落在**交集**里——概率就是 |交|/|并|，正好是 Jaccard。

所以 128 个哈希里有多少个位置相等，除以 128，就是 Jaccard 的无偏估计。两篇文档的相似度，从"比对两个巨大集合"变成了"数两个 128 维签名有几位相同"。

**第三步，LSH：让相似的自动撞到一起。**还是不能逐对比签名（依然 O(n²)）。把 128 维签名切成 16 段（band），每段 8 维；**任何一段完全相同**的两篇文档进同一个桶，只有同桶的才算候选对。这个设计造出一条陡峭的 S 形曲线——设两篇文档相似度为 s，至少撞上一段的概率是 1 − (1 − s⁸)¹⁶：

```text
s = 0.9（近似重复）  →  撞桶概率 ≈ 99.99%   几乎必然成为候选
s = 0.3（不太相关）  →  撞桶概率 ≈ 0.1%     几乎必然被跳过
```

相似的几乎全被抓到，不相似的几乎全被放过——"该比较谁"被概率自动筛了出来。

**第四步，精确验证。**对候选对算真实的 Jaccard，超过阈值（通常 0.8）删掉一份。

## 4. 序列打包：别为 padding 烧钱

先把问题本身说清楚。GPU 高效计算的前提是**矩形张量**：一个训练批次必须是"批大小 × 固定序列长度"（比如 8 × 2048）的整齐方阵，每一行恰好 2048 个 token，一个不多一个不少。而清洗完的文档天然长短不一：有的 50 token，有的 5 万。矛盾就在这：**变长的文档，怎么填进定长的行？**

**天真做法：一篇文档占一行，不够的补 padding。**一篇 200 token 的文档，后面垫 1848 个 PAD 占位符。PAD 不参与损失、什么都不教模型，但前向传播照样要算它——它占着位置烧算力。用三篇文档（200、500、100 token）算笔账：真实 token 共 800 个，占用的位置是 3 × 2048 = 6144 个，**利用率 13%，87% 的算力在空转**。

**打包做法：文档首尾相接成一条连续的 token 流，再按 2048 一刀刀切开。**

```text
token 流：  [文档A 的 1000 个 token] EOS [文档B 的 600 个] EOS [文档C 的 900 个] EOS [文档D…
切分：      |—————————— 第 1 行（恰好 2048）——————————|—————————— 第 2 行（恰好 2048）——————…
```

每一行都被真实 token 填满——语料够大时，只有整个数据集的最后一行才需要 padding，利用率逼近 100%。文档之间的 EOS 分隔符不是摆设：模型在训练中反复见到"EOS 之后话题突然换了"，从而学会 EOS = 上下文重置——这正是推理时模型知道"话说完了"的来源。

打包换来了效率，也带来一个新问题：**一行里现在住着好几篇互不相干的文档。**默认的因果注意力只挡"看未来"，不挡"看邻居"——文档 B 的 token 会把前面文档 A 的内容当作自己的上下文。物理上是邻居，语义上是陌生人：让模型根据一篇球赛报道去预测菜谱的下一个词，学到的是纯噪声。解法是**块对角注意力掩码**，在因果掩码的基础上再把跨文档的注意力清零。一行装着文档 A（3 个 token）和 B（2 个 token）时，掩码长这样（✓ = 允许注意，· = 屏蔽）：

```text
查询\键    A1   A2   A3   B1   B2
  A1       ✓    ·    ·    ·    ·        ← 因果：只能看自己和过去
  A2       ✓    ✓    ·    ·    ·
  A3       ✓    ✓    ✓    ·    ·
  B1       ·    ·    ·    ✓    ·        ← 块对角：B 看不到 A
  B2       ·    ·    ·    ✓    ✓
```

只有因果掩码时，左下角那块会全是 ✓（B 能看 A）；块对角掩码把它清掉，每篇文档在注意力里活成一座孤岛。两个务实的注脚：早年不少管线（GPT-2/GPT-3 时代）其实偷懒不做块对角，只靠 EOS 让模型自己学会忽略跨文档内容——短上下文时代影响有限；Llama 3 论文明确说他们做了跨文档屏蔽，并指出在长上下文训练阶段这一点变得重要——序列越长，一行里塞的无关文档越多，噪声越不能忍。

还有两个细节决定成败：

- **超长文档的切分点有讲究**：5 万 token 的文档要横跨几十行，行与行之间在训练时是独立打乱的——被切开的后半段拿不到前半段的上下文，只能"冷启动"。从句子中间硬切，模型看到的就是没头没尾的残缺思想；好的管线尽量把切口对齐到段落或句子边界。
- **盯住利用率指标**：非 padding token 占比应在 90% 以上（充分打包时接近 100%），低于这个数说明打包策略在浪费算力。

## 5. Chinchilla：给定算力，参数和数据怎么分

这是全课最根本的问题，也是原文只给了结论的地方——`N_opt ~ C^0.5, D_opt ~ C^0.5`。这个 0.5 是从一条完整的公式链条里解出来的（Hoffmann et al. 2022，用 400 多次训练拟合），值得亲手走一遍。

**先看它推翻了什么。**更早的 Kaplan 缩放律（2020）给的指数是 N ∝ C^0.73、D ∝ C^0.27——"算力涨了，主要拿去堆参数"。GPT-3（175B / 300B token）、Gopher（280B / 300B token）都是照这个哲学设计的。Chinchilla 指出这个偏差主要来自实验设置问题（学习率日程没有和训练长度匹配），修正后结论完全反转。

### 公式一：损失是 N 和 D 的函数

```text
L(N, D) = E + A/N^α + B/D^β

拟合常数：E = 1.69,  A = 406.4,  B = 410.7,  α = 0.34,  β = 0.28
```

三项各有明确含义：

- **E = 1.69，不可约损失**：模型无限大、数据无限多也降不到 0——这是自然语言本身的熵，文本里真正随机的部分。
- **A/N^α，模型太小的罚款**：容量不够，再多数据也装不下。
- **B/D^β，数据太少的罚款**：数据不够，再大的模型也只能把这点东西背熟。

**"undertrained" 在这个公式里有了精确定义**：算力花在了压第二项（堆参数），而损失的大头卡在第三项（缺数据）。Gopher 就是教科书案例——280B 参数把第二项压得很低，300B token 让第三项高高挂起。

### 公式二：算力恒等式

```text
C ≈ 6 · N · D
```

训练时每个参数在每个 token 上花约 6 FLOPs（前向 2 + 反向 4）。这个近似把"算力预算"变成了 N × D 的硬约束：**预算固定时，参数和数据此消彼长**，问题从"都要"变成"怎么分"。

### 公式三：约束下的最优解

在 6ND = C 的约束下最小化 L(N, D)，闭式解是：

```text
N_opt ∝ C^a,   D_opt ∝ C^b,   其中 a = β/(α+β),  b = α/(α+β)
```

论文用三种独立方法各估了一遍（固定模型扫数据、IsoFLOP 剖面、参数化拟合），得到 a/b 分别为 0.50/0.50、0.49/0.51、0.46/0.54——殊途同归到 **a ≈ b ≈ 0.5**。这就是原文那两行公式的出处：**算力翻倍，参数和数据各扩 √2 倍，等比例长大。**换算成实用法则：**每个参数配约 20 个 token**（D ≈ 20N）。

这个"20"值得较真一下——它不是拟合出来的自然常数。20.0 恰好是 Chinchilla 自己的训练配置（1.4T ÷ 70B），是设计出来的整数；论文 Table 3 用拟合**外推**的最优配置，比例其实随算力缓慢上升：Gopher 预算下最优是 67B + 1.5T（每参数 **22.4** 个），175B 规模对应 3.7T（**21.1** 个）。三种方法里有两种给出 b 略大于 a，意味着比例本就该随规模微微变大；Epoch AI 复现修正后的集中估计仍在 20 上下。工程上的正确读法是：**把 20 当量级，别当常数**——它只对"训练算力最优"这个目标成立；随数据质量漂移（DeepSeek 自己的缩放研究发现数据质量越高，算力越该偏向参数）；连"token"这个计数单位本身都是分词器定义的，同一语料换个词表，分子不动分母就变了。

拿课文的数字验算：Chinchilla 70B × 20 = 1.4T token，正是按这个比例设计的；6 × 70B × 1.4T 和 Gopher 的 6 × 280B × 300B 在同一档算力——**同样的预算，不同的分法，全面胜出**。GPT-3 的算力（约 3.15 × 10²³ FLOPs）若按 Chinchilla 分配，应该是约 50B 参数 + 1T token；它实际是 175B + 300B——参数多了 3.5 倍，数据少了 3 倍多，这就是"undertrained 3-4x"的出处。

| 模型 | 参数 | 训练 token | 每参数 token 数 | 按 Chinchilla 的判词 |
|---|---|---|---|---|
| GPT-3 | 175B | 300B | ~1.7 | 严重欠训练 |
| Gopher | 280B | 300B | ~1.1 | 严重欠训练 |
| Chinchilla | 70B | 1.4T | 20 | 最优（按设计） |
| Llama 2 70B | 70B | 2T | ~29 | 故意过训练 |
| Llama 3 70B | 70B | 15T | ~214 | 重度过训练 |

### 为什么 2024 年之后大家又"故意违反"它

表格最后两行不是打脸，是换了目标函数。**Chinchilla 的"最优"只对训练算力最优——公式里根本没有推理成本这一项。**而两种成本的付费方式完全不同：训练费付一次，推理费按 token 付一辈子，且每生成一个 token 约花 2N FLOPs——**参数量 N 是挂在每一次服务上的持续负债，训练 token 数 D 却只在训练时收费**。

先纠正一个自然但错误的读法：**不是"数据多让推理变便宜"——是"模型小让推理变便宜"，数据多只是让小模型不掉质量的补偿品。**推理成本的公式里只有 N，没有 D：前向传播只跑权重，不问权重是拿多少数据学出来的。对照损失公式看得最清楚：A/N^α 是**容量罚款**，它的账推理时每次都要付（参数摆在那，每个 token 都得全部乘一遍）；B/D^β 是**见识罚款**，把它压低的成本（多喂数据）训练时一次付清，推理时分文不花。inference-optimal 的本质，就是沿着等质量曲线，**把质量负担尽量从"持续付费的容量项"挪到"一次付清的见识项"**。当然挪不到无穷远：β < 1 意味着数据收益递减，模型每再缩一点，需要的补偿数据成倍上涨；而且固定 N 时损失永远压不破 E + A/N^α 这个容量地板——8B 喂无限数据也变不成 400B。

一笔示意账感受量级：同等质量下如果能把参数从 70B 换成 35B，一个上线后要生成 10 万亿 token 的模型，推理端省下 2 × 35B × 10T ≈ 7×10²³ FLOPs——**比 Chinchilla 整个训练预算（约 5.9×10²³）还多**。所以最优点大幅偏向"更小的模型 + 远超 20:1 的数据"：沿着等损失曲线，用多付的训练费换永久便宜的推理。这个思路其实 LLaMA 第一代论文（2023 年初）就已经写明——"Hoffmann 的目标函数忽略了推理预算，我们选择把更小的模型训得更久"；Llama 3 8B 用 15T token（每参数近 1900 个）把它推到极致，业界称为 **inference-optimal**，2024 年后成了行业默认。注意它不是一条像 Chinchilla 那样的单一定律：最优比例取决于你预估这个模型一生要服务多少 token，所以各家的 token/参数比五花八门——形式化的处理见《Beyond Chinchilla-Optimal》。

两句学术后记：Epoch AI 的复现研究发现原论文第三种方法的拟合有小瑕疵，修正后三种方法完全一致——结论反而更稳了；把推理成本正式写进公式的后续工作见《Beyond Chinchilla-Optimal》。

## 6. 收尾：一条恒等式改变了数据的地位

把整课收在一个观察上：**C ≈ 6ND 这条不起眼的恒等式，把"数据多少"从工程细节升格成了和"模型多大"平起平坐的一等公民。**在它之前，数据管线是脏活累活；在它之后，每一个 token 都是算力预算表上的一行——来源配比（第 1 节）决定这些 token 值不值，清洗去重（第 2、3 节）决定有多少 token 是真的，打包（第 4 节）决定有多少算力真正花在 token 上，而 Chinchilla（第 5 节）告诉你总共该买多少 token。

镜子的比喻到这里可以补完整了：模型是一面镜子，数据管线决定镜子面前站着的是谁。
